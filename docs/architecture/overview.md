# Proposed architecture — Phase 0 baseline
Status: proposed cloud design with a locally implemented Phase 5 application plus offline-validated Phase 6 cloud definitions. Catalog and booking domains, stored prices, local test-payment confirmation, signed tickets and booking history now run against PostgreSQL. Signed developer identities are local-only; real Cognito code is offline-tested but actual managed login is unverified. Gate/ride and profile/admin operations now exist; durable local worker consumption and stored Metabase SQL reporting now exist. AWS deployment remains future work. See phase-4-outcome.md.

React/TypeScript/Vite/Tailwind will be hosted by Amplify. Cognito supplies user authentication; each backend validates JWT signature via JWKS, issuer, expiry, access-token client_id/token_use and admin group or visitor ownership. API Gateway HTTP API provides external routes and JWT authorization. A VPC link connects to an internal ALB managed by the AWS Load Balancer Controller. ALB path routing targets EKS services/pods. Map away API Gateway stage prefixes. Explicit HTTPS private integration requires a certificate/name and tlsConfig; include pod TLS or a TLS proxy if claiming encryption over every hop. No public service bypass of authorization is permitted.

Source: [AWS private HTTP integrations](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-develop-integrations-private.html), checked 13 October 2026. Domain/certificate provisioning and verified end-to-end TLS remain P6 gates.

| Service | Owns | Deployable boundary | Planned database permissions |
|---|---|---|---|
| Attractions | Catalog and retirement | Own process, image and Deployment | attractions schema read/write only |
| Booking | Tiers, price snapshots, bookings, payments, ticket issuance | Own process, image and Deployment | booking schema read/write only |
| Gate/ride | Ticket validation, arrivals, ride events, visit history | Own process, image and Deployment | visits schema read/write only |
| Analytics worker | Event deduplication and reporting projection | Worker plus health server in own Deployment | reporting writes, outbox access only where explicitly granted |
| Metabase | Dashboards, query metadata | Local optional profile; private AWS deployment later | reporting SELECT; separate metadata database |

A single PostgreSQL instance lowers demo cost, but separate schemas and roles enforce ownership. This shares a database failure domain; it is not full independent storage. Phase 4 implements attractions, booking, visits and reporting schemas plus separate restricted service roles and a view-only BI login. The development-only owner is reserved for migrations/seeds and is not passed to API processes. Metabase never receives the operational owner credential for reporting.

Proposed AWS demo network: two AZ public subnets for managed workers with public egress and no inbound internet rules, two private subnets for internal ALB/VPC link and RDS. Avoid NAT for this limited demonstration. Public worker addresses incur charges and require careful security groups; private-worker production topology needs costed NAT/endpoints. Private EKS API access for nodes plus restricted public API access for the operator. One worker is a cost minimum, not HA; two are needed for node-failure demonstration. Size from measured memory including Metabase and system pods, not wishful micro-instance capacity.

## Data and partial failure design (future)
Booking creation records a pending booking and price snapshot. Verified payment atomically confirms the booking and writes the purchase outbox event. Only a verified provider webhook may transition payment/booking to confirmed; unique provider event IDs and conditional state transitions prevent duplicate confirmation. Booking command idempotency key binds to user plus payload hash. Prices use integer cents; all event times UTC, reporting timezone configurable (initial assumption Asia/Colombo). Capacity/double-booking rules are unresolved; do not invent park capacity.

Planned transactional outbox publishers retry to SQS with bounded exponential backoff/jitter. Delivery is at least once; the worker inserts a unique event ID and projection updates in one transaction, deleting a queue message only after commit. DLQ handles poison messages. Booking remains usable during analytics failure; dashboards show projection lag. A DB outage remains a shared limitation. CQRS does not require implementing full event sourcing.

Gate verifies an RS256 ticket independently of booking, records one full-party arrival and guest count atomically with an outbox event, and does not support cancellation/refunds. No revocation projection exists yet; signatures alone cannot detect a future refund, so revocation/freshness policy is required before adding refunds. Ride events require a valid checked-in booking, attraction, timestamp and guest count; do not bypass validation when a dependency fails. Catalog failure need not block an already priced booking. Payment outage leaves a pending booking; never invent a successful payment.

## Reporting model (future P4)
`reporting.purchases`, `reporting.arrivals` and `reporting.rides` contain minimized event facts with event IDs, occurred_at, booking references and the appropriate guest counts/tier/attraction/money fields. No visitor names or tokens are stored. Tier and attraction label snapshots are allowed. Arrival totals sum guest_count; purchased tickets count confirmed bookings grouped by snapshot tier; revenue sums confirmed amount_cents; popularity sums ride guest_count (also expose event count); hourly buckets include open hours with zero events for quiet periods. Reporting timezone is Asia/Colombo and opening hours are provisionally 09:00–18:00; refunds remain unsupported. Metabase reads stored facts with read-only role. Keep metadata separate and back it up or provision dashboards repeatably.

## Local versus cloud
Compose DNS provides local names, PostgreSQL volume persists development data, and optional Metabase connects locally. Compose is not a substitute for Minikube evidence. The durable local worker and seven private Metabase questions are implemented and SQL-verified. Terraform bootstrap/persistent and temporary demo resources have separate states; ordering is in architecture-decisions and roadmap. Local Kubernetes workloads, service discovery, probes, HPA and release/failure scripts are implemented in Phase 5. Four real Terraform roots and guarded cloud lifecycle commands are implemented and validated offline in Phase 6; no AWS deployment occurred.

## Initial tier configuration for Phase 2
The assignment p2 prices are indicative; the user requests them as initial stored values: Individual exactly 1 guest / USD 40 (4000 cents), Couple exactly 2 / USD 75 (7500 cents), Family up to 4 / USD 140 (14000 cents), Group up to 5 / USD 165 (16500 cents). Minimum Family/Group count is provisionally 1 pending review; do not confuse tier capacity with actual arrival count. Prices belong in seeded database rows, editable by administrators, with a snapshot copied into each booking. Phase 2 seeds these rows non-destructively, reads them in the frontend and tests price snapshots; pricing/tier management UI is built in Phase 3 and awaits interactive review.

## Phase 4 implemented local read path
The analytics service now publishes booking/visits outboxes into reporting.queue and projects deduplicated purchases/arrivals/rides. Local queue delivery and source acknowledgment are atomic on the shared database. Facts, deduplication and completion commit together. The reporting role has only SELECT and published_at UPDATE on source outboxes; it cannot read operational bookings. Metabase uses a separate login with SELECT only on aggregate views. Native Metabase and the protected admin Analytics tab query stored reporting data. See docs/diagrams/analytics-pipeline.mmd and docs/archive/phases/phase-4-outcome.md. Actual SQS is still a future cloud integration, with the adapter verified offline only.

## Phase 5 local runtime
A named Colima VM hosts the wonderland Minikube profile (Kubernetes 1.37.0). Two catalog/booking replicas plus gate, analytics, nginx and a persistent single-node PostgreSQL database run separately from native mode. The local proxy forwards to ClusterIP APIs and gate resolves catalog service DNS. Images are built/loaded locally, secrets generated privately, and migrations complete before API rollout. Live pod replacement, blue-green routing/rollback, worker backlog recovery and DB readiness/PVC persistence demonstrations are recorded in docs/archive/phases/phase-5-outcome.md. The cloud network/API Gateway design remains proposed.

## Phase 6 prepared cloud path
Bootstrap/persistent/demo/edge states define backend and reusable assets separately from temporary VPC/EKS/RDS/SQS and gateway resources. Approved operator scripts provision secret versions outside Terraform state, build/push images, install the pinned controller/metrics/logging components, migrate before rollout, discover the actual listener, publish edge/Amplify and verify or clean up in reverse dependency order. AWS-generated workloads replace local identities, transport and storage with Cognito, SQS/IRSA, verified RDS TLS and internal HTTPS. Native/Minikube services remain separate. See docs/advanced/eks-runbook.md for actual commands and unverified cloud limits.
